# /shodan — 初回商談の準備

新規企業との**初回MTG前**に、事前情報と公開情報だけから提案書ドラフト（pptx）を作る。
議事録がまだ存在しない段階が対象。既存顧客への提案は `/teian` を使うこと。

入力: `$ARGUMENTS`

---

## 進め方の原則：途中で止まらない

**このコマンドは最後まで自走する。ユーザーに選択肢を出して判断を仰がない。**

迷う場面は必ず出るが、**その場で自分で決めて進み、決めた内容と根拠・却下した案を STEP 7 でまとめて報告する**。事後に報告すれば人はいつでも覆せる。逐一聞くと、作業が人の待ち時間で分断されて意味がなくなる。

途中で止まってよいのは次の2つだけ。どちらも**進むと出力が壊れる**場合である。

1. **企業名がプレースホルダー／実在しない**（STEP 0）— 調査対象が特定できず、何も作れない
2. **Notion の読み取りが失敗した**（STEP 1）— 静的記述で代用すると嘘の根拠を作る

この2つ以外で「どちらにしますか？」と聞かないこと。訴求軸・型・価格レンジ・構成の取捨選択は、すべて自分で決める。

---

## STEP 0. 入力を整理する

第1引数を企業名として扱う。残りは事前情報として自由記述で受け取る。事前情報には次が混ざりうる:

- 紹介者・紹介経路（**受注の8割が紹介**。誰からの紹介かは最重要）
- 面談に至った経緯、先方から届いた問い合わせ文面
- 先方の関心事、決裁者、参加予定者
- MTGの日時・形式
- もらった資料のファイルパスやURL

事前情報が空でも止まらない。企業名だけで進め、埋まらなかった項目は最後に「MTGで聞く論点」に回す。

**ただし企業名がプレースホルダーの場合は、調査に入る前に止めて聞き返す。** `〇〇株式会社` `◯◯` `XX社` `A社` `test` `サンプル` など、実在の社名でないものが渡されたときは、WebSearchを実行せずにその場で実際の社名を尋ねる。実在しない社名では固有名詞も数字も拾えず、専用感のある提案書は作れない。検索を1回無駄に回さないため、ここで先に弾く。

## STEP 1. 既存かどうかを先に確認する

**3つのDBすべてを読む。クライアントマスタだけでは足りない。**

1. **クライアントマスタ** — 取引先として登録済みか
2. **拡張案件** — 「〇〇 ― 状況要確認」のように、過去の検討経緯だけが残っている場合がある
3. **提案トラッキング** — 過去に提案を出して失注・保留になっていないか

クライアントマスタに無くても拡張案件に記録があることは実際にある。3つとも当たらずに「新規です」と判断すると、社内に残っている経緯を無視した提案になる。

ID は CLAUDE.md の「Notion 営業基盤 DB構成」表から引く（毎回検索しない）。

**必ず `notion-eigyo` サーバを使う。`notion` サーバではない。**

`.mcp.json` には Notion サーバが2つある。ワークスペースが別で、どちらにも `ehonAI` という同名の integration がいる。

| サーバ名 | ワークスペース | 中身 |
|---|---|---|
| `notion` | Ehon Inc. | 記事ネタ帳・記事ページ（コンテンツ制作用） |
| `notion-eigyo` | えほんインク | **ÉHON 営業基盤の全DB** |

`notion` を使うと営業基盤は404になる。同名なのでエラーメッセージだけでは見分けがつかない。

claude.ai の Notion コネクタが使える環境なら、そちらはビュー実行モード（`mode:"view"` + view URL）で読む。SQLモードは使わない（クォータを使い切ると全機能が止まる）。

判定:

- **既にある場合**: このコマンドの対象外。既存の記録（ステータス・累計売上・直近請求日・備考・関連提案）を提示し、「既存顧客のため `/teian` の領域です」と述べて**終了する**。どちらにするか聞かない。ただし引数に「別部署向け」「新規事業として」など初回提案を求める趣旨が明示されていれば、確認せずそのまま続行し、既存の記録を STEP 3 の材料に加える。
- **ない場合**: 新規として続行。

### 読み取りに失敗したら、そこで止める

**Notion の読み取りがエラー（404 / unauthorized / タイムアウト等）を返したら、その時点で処理を止めてユーザーに報告する。**

絶対にやってはいけないのは、**CLAUDE.md の事業概要や進行中プロジェクト一覧で代用して判定を続けること**。CLAUDE.md は静的な前提であり、案件の現在地ではない。「鈴木自工＝アバター絵本」のような記述は書かれた時点のスナップショットで、Notion 上の実際の状態（継続納品中か、累計いくらか、進行中の提案が何本あるか）とは別物である。静的記述で「既存です」と答えると、結論がたまたま合っていても根拠が嘘になり、次は間違える。

404 が返る場合、原因はほぼ次のどちらか。報告時にこの2つを候補として挙げる。

1. Notion の integration が対象ページに接続されていない → Notion で親ページ「ÉHON 営業基盤」を開き、⋯ → 接続 → 該当の integration を追加する（配下のDBは一括で見えるようになる）
2. ID の種類違い → `database_id` を渡すべきところに `data_source_id` を渡している（またはその逆）。CLAUDE.md の表には両方載せてある

## STEP 2. 公開情報を調査する

WebSearch で調べる。観点は次の5つに固定する。

1. 設立年・周年のタイミング（**次の節目は何年後か**を必ず計算する）
2. CSR・SDGs・社会貢献の取り組み
3. ギフト・ノベルティ・記念品の施策実績
4. 直近のプレスリリース（新規事業・周年・採用強化）
5. 決裁構造（代表者名、広報・マーケ責任者が公開されているか）

加えて、提案書の専用感に直結する具体的事実を拾う。**社員数・創業年・拠点数・取扱品目数・発信本数など、数字で言えるもの**を優先する。芋慶の提案書が効いたのは「木桶」「蔵付き微生物」「信長の兵糧」という固有名詞が入っていたからで、抽象語で埋めた提案書は初回で見抜かれる。

**数字や固有名詞が出典によって食い違ったら、勝手に1つ選ばない。** 従業員数・代表者名・設立年は求人サイトと公式サイトで食い違うことが多い。**公式サイト（自社ドメイン）を最優先**とし、それでも割れる場合は両方を併記してSTEP 7の論点に送る。とくに**代表者名の漢字は必ず公式の会社概要ページで確認する**。相手の代表名を誤字った提案書は、内容以前に信用を失う。

**禁止**: 見つからない項目を推測で埋めないこと。「公開情報では確認できず」と書き、STEP 7 の論点に送る。出典URLは全項目に付ける。事実と推測は必ず分けて書く。

## STEP 3. 訴求軸を決め、型を分岐する

**まず `.claude/references/ehon-offerings.md` を読み、「何を提案するか（商材）」を決める。** 業界から商材を引く表がある。型はそのあとで選ぶ。

商材を先に決めないと、業界に合わない施策と事例を引きずる（婚活の提案書に自動車の施策を入れた失敗がある）。**候補が複数あっても提案書に載せるのは1商材だけ。**

商材が決まったら `.claude/references/ehon-proposal-formats.md` を読み、型を選ぶ。

調査結果から訴求軸の候補を3つ挙げ、**その場で1つに決めて進む。ユーザーに選ばせない。** 2案並べると先方が選べず持ち帰りになるため、提案書に載せるのは1軸だけ。却下した2つは STEP 7 で「落選させた訴求軸」として報告し、口頭補強メモに回す。

引数で軸が指定されていればそれに従う。指定がなければ、次の順で自分で決める。

1. 事前情報に先方の関心が書かれていれば、それに最も近い軸
2. 周年が3ヶ月以内に来るなら「周年」
3. 業態から、顧客接点が多く記念品の余地がある業種なら「販促・ギフト」
4. どれにも当たらなければ「創業ストーリー」（ナラティブ型の既定）

**周年が過ぎている・数年先である、といった理由で手が止まったら、周年を捨てて次の軸に移る。** 案件を追うか捨てるかの判断をユーザーに投げない。

軸に応じて型が決まる（判別表は references の冒頭）。

| 訴求軸 | 型 |
|---|---|
| 周年 / 創業ストーリー / サービスの想い | ナラティブ型（references §1） |
| 販促 / ギフト / システム | 販促・仕組み型（references §2） |
| 採用 | 伴走型 → skill `ehon-companion-proposal` を使う |

判別できなければナラティブ型を既定とする。

**伴走型に分岐した場合の注意**: `ehon-companion-proposal` は Step 1 で議事録を要求するが、初回MTG前には存在しない。議事録の代わりに STEP 0 の事前情報と STEP 2 の調査結果を入力として扱い、「クライアントが言語化している課題」は**仮説である**と提案書内で明示する。断定すると外したときに取り返しがつかない。

## STEP 4. 提案書の中身を組む

選んだ型の構成に従って、各スライドの本文を書く。

- **STEP 2 で拾った固有名詞と数字を本文に直接書き込む。** これが「この会社のために作られた」と伝わる唯一の手段。
- **先方の強みを課題として扱わない。** 調査で「既にできている」ことが分かった領域を改善提案の軸にすると、理解していないと受け取られる。
- サンプルシナリオとキャラクター案は**仮案であることを明記**する。先方の素材を見る前に確定案として出すと後で覆せない。
- 実績・実証データは references §5 から選ぶ。数値には出典を併記し、「必ず〇%上がる」と断言しない。
- 代理店経由の案件（芋慶・THE BALLET SHOW → グローバルパートナーズ／アテニア → DNP）は、社名を出す前に許可が要る。未確認なら業種表記にする。
- 価格は references §4 に従い**概算レンジ**で出す。確定金額は出さない。

**社外版に絶対に書かない（違反例が実際に出ている）**

- **他社の取引額・請求額・売上**。「鈴木自工 累計売上2,572,350円」のように、別の顧客がいくら払ったかを第三者に開示してはならない。実証データとして出すなら「継続納品中のカーディーラー1社」「大手生命保険会社」のように**金額を伏せた表記**にする。
- 粗利率・粗利額（GIVENESS&CO 79.5% など）
- FC100店舗モデル 年間粗利264万円（仮置きで根拠が固まっていない）

**初回提案でシステム開発を前提にしない**

「AI生成システム構築 50万円」のような初期開発費を初回に積むと、旭化成ホームズと同じ結末になる（開発工数が大きくスケールしないと判断され失注）。初回は**既存の仕組みで回せる範囲**で構成し、システム化は「規模が見えてからの第2段階」として口頭補強に回す。

**印刷単価は有効期限を必ず確認する**

印刷単価マスタの `見積日` を見て、**錦明印刷は3ヶ月、三恵社は2ヶ月**を過ぎていたらその単価を概算に使わない。使わざるを得ない場合は「再見積が必要」と明記し、STEP 7で報告する。期限切れの単価で見積もると赤字になる。

## STEP 5. pptx を生成する

**`.claude/lib/ehon_deck.py` の部品関数を使って組む。デザインを自分で再構築しないこと。**

散文の仕様書から色や書体を毎回組み直すと必ずズレる（実際に汎用の青＋オレンジになった失敗がある）。パレット・書体・部品の寸法はすべてこのモジュールに固定してあるので、**呼ぶだけでトンマナが揃う**。

```python
import sys; sys.path.insert(0, ".claude/lib")
from ehon_deck import *

prs = new_deck()
cover(prs, eyebrow="ÉHON INC. × 〇〇株式会社", title="...", sub="― ...", date="2026年8月27日 ／ ドラフト")

s = slide(prs, "見出し", "サブコピー")          # 見出し左のワイン縦バーが自動で入る
# 座標は書かない。見出しの下から自動で積まれる
cards_row(s, items=[                             # 横並びは必ずこれ（高さが揃う）
    {"title": "① ...", "accent": NAVY, "lines": ["...", "..."]},
    {"title": "② ...", "accent": WINE, "lines": ["...", "..."]},
    {"title": "③ ...", "accent": GOLD, "lines": ["...", "..."]}])
note_block(s, title="...", body="...")           # カードの下に自動で置かれる
flow(s, items=["契約", "制作", "納品", "再来店"])
card(s, title="...", lines=[...])                # 単体。全幅で積まれる
big_number(s, 0.62, 1.7, 3.0, "指標名", "90", "%", "補足")
split_bar(s, 0.62, 1.7, 12.1, [("制作費", "50万円〜", 45, NAVY), ("印刷費", "別途", 55, WINE)])
flow(s, 0.62, 1.75, 12.1, ["契約", "制作", "納品", "再来店"])
note_block(s, 0.62, 4.1, 12.1, 1.2, "見出し", "本文")
conclusion(s, "言い切りの一文")                  # 1スライド1本まで

assert_fits(prs)          # ← 必須。はみ出していたら例外で止まる
prs.save("output/YYYY-MM-DD_{企業名}_初回提案.pptx")
```

使える色定数: `WINE`（主）/ `NAVY`（副）/ `GOLD`（第3）/ `ROSE`（中間調）。**この4色以外を指定しない。**
3カテゴリを横に並べるときは `NAVY → WINE → GOLD` の順にする。

### 提案書として成立させるための3点（保存前に必ず自己点検する）

実行結果で「提案として成立していない」と評価された失敗が出ている。pptxを保存する前に、次を自分で確認すること。

**1. 見出しと中身が一致しているか**
「絵本がパーソナライズする要素」という見出しのスライドに、先方の成婚率・マッチング率を並べた失敗がある。1枚ずつ、見出しを読んでから中身を読み、噛み合っているか確かめる。別のスライドの見出しが本文に紛れ込んでいないかも見る。

**2. 事例が提案先と関係しているか**
婚活の提案書に自動車の事例を2枚入れた失敗がある。`references` の「実績は提案先と関係があるときだけ載せる」に従い、**関係する実績がなければ実証データのスライドごと落とす。** 埋めるために持ってこない。

**3. 空欄・プレースホルダーが残っていないか**
`---`、`TBD`、`（未確認）` が1つでも残っていたら、その項目をスライドから削除する。3つ並べる予定で2つしか埋まらなければ2つで組む。

**提案する施策は1つに絞る。** 絵本とガチャ、記念品とシステム開発のように、性質の違う施策を1つの提案書に混ぜない。混ぜると先方が何を検討すればよいか分からなくなる。

### 構成の作り方（スカスカにしない）

実行結果で、課題を1枚ずつ別スライドに分けて13枚に薄く散らし、下2/3が空白になる失敗が出た。次を守る。

- **1スライドに1カードだけ、という構成にしない。** カードは2〜4枚を横並び（`cards_row`）にして1枚にまとめる。
- **課題・活用シーン・価値のような並列項目は、必ず1スライドに収める。** 「課題①」「課題②」で3枚に割らない。
- **スライドの下半分が空くなら、内容が足りないか、分けすぎている。** 統合するか、`big_number` や `flow` で面を使う。
- 枚数は **10〜12枚**を目安にする。多いほど良いわけではない。
- 同じ見出しを2枚以上のスライドで繰り返さない。

**カードを横に並べるときは `cards_row()` を使う。** `card()` を並べると、タイトルの行数差で下端が不揃いになる。

**カードのタイトルは全角14文字以内**にする。超えると2行になり、1文字だけ2行目に落ちて間延びする。

**座標（x, y）と高さを書かない。** `slide()` が見出しの下から縦位置を持っていて、部品はそこに積まれ、自動で下へ送られる。手で座標を決めると要素が重なる（注記ブロックがカードに覆いかぶさる事故が実際に出た）。

横幅を狭くしたいときだけ `w=` を渡す。左右に並べたいときは `cards_row()` に任せる。

詰め込みすぎていないかは `overflowing(s)` で確認できる。`True` なら結論帯にぶつかっているので、項目を減らすかスライドを分ける。余白を足したいときは `space(s, 0.3)`。

**モジュールに無い表現が必要になったら、その場で図形を描かずに `ehon_deck.py` へ関数を足す。** 一度足せば次回以降も揃う。

体裁の詳細は `.claude/references/ehon-deck-design.md` を参照（禁止事項もそこにある）。要点だけ再掲すると、**イラストは入れない／罫と矢印を文字で代用しない／余白を埋めない**。

表紙の日付は `YYYY年M月D日` で `日` を落とさない。「ドラフト・本日時点の公開情報に基づく」を必ず添える。

## STEP 6. Notion に登録する

クライアントマスタに新規レコードを作成する。

- ステータス: **相談レベル**
- 企業名 / 相手区分 / 接点の起点 / 紹介者 / 決裁者（判明分のみ）
- 想定用途: STEP 3 で選んだ訴求軸
- 備考: 当たり所メモを300字以内で。先頭に `【YYYY-MM-DD 更新】` を付ける

既存レコードがあった場合は**備考欄に追記する。上書きは禁止**。長期の検討メモが蓄積されているため、機械的な上書きは事故になる。

## STEP 7. 最後に必ず出す3点

pptx を作って終わりにしない。ターミナルに次を出力する。

1. **使った事実と出典** — 提案書に書き込んだ固有名詞・数字を、出典URLとセットで一覧にする。MTG前に本人が裏を取れる形にする。
2. **確認できなかった項目** — 「公開情報では確認できず」とした項目。憶測で埋めていないことを明示する。
3. **MTGで聞く論点** — 提案の前提のうち、外れていたら構成が変わるもの。落選させた訴求軸2つもここに含める。

## この提案書が外しやすい前提（毎回意識する）

初回提案は情報が足りない状態で作るため、次の3つを外しやすい。作りながら疑うこと。

- **先方が既に解決していることを課題として提案する** — 調査で拾えるのは外向きの情報だけ。社内の実態は分からない。
- **感動を買う理由だと思い込む** — ガリバー案件では満足度約90%を取りながら、ディーラーが金を払う理由（再来店率・売上・保険加入率）のデータが3年空欄のまま停滞した。満足度は購入理由にならない。
